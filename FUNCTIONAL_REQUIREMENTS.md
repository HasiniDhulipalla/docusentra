# Official Snovasys TrustVault requirements — acceptance matrix

This matrix maps the organizer's ten requirements supplied in the challenge brief to the current implementation and its evidence. A checked test is evidence for the code path it exercises, not proof that an Internet-deployed system is secure against every attack.

| # | Official requirement | Implementation / acceptance behaviour | Evidence and remaining limitation |
|---:|---|---|---|
| 1 | Authentication with administrator, document owner and viewer roles | `User.system_role` is `admin`, `owner`, or `viewer`; public registration cannot choose a privileged role. The seeded admin can manage roles. Per-document grants are separately `reader` or `editor`. A system administrator does not gain document-content access unless owner/shared. | `backend/app/seed.py`, `/api/admin/users`, `PATCH /api/admin/users/{id}/role`, `test_challenge_requirements.py`. The local seed credentials are for development only. |
| 2 | Upload, organise, search and manage documents | Upload, category, list/search, rename, share, and soft-delete. Search filters are server-side and operate only on documents owned/shared with the caller. | `GET /api/documents?q=&owner=&category=&from_date=&to_date=`; upload/search tests. No nested folders/version history in this MVP. |
| 3 | Per-document read and edit permission granted to named people | Owners grant/update named users by username/email as `reader` or `editor`; each protected route resolves current owner/share role server-side. | `POST/GET/DELETE /api/documents/{id}/shares`; API flow tests. |
| 4 | Owners grant and revoke access | Share grant/update/revoke operations are owner-only. Every request checks current share state, so revocation blocks the next request. | Revocation test covers download and the preview routes after the share row is removed. It cannot erase a file already downloaded by an Editor/Owner. |
| 5 | Ungranted users cannot read, download, change or delete | Protected document endpoints check ownership or an active share. Readers cannot download/rename/share/delete. Admin role alone never bypasses document grants. Denials return 403 for existing inaccessible documents (404 for missing/deleted IDs). | `backend/tests/test_api_flow.py`, `backend/tests/test_challenge_requirements.py`; includes direct API calls rather than just hiding UI controls. Continue to test the final deployed URL. |
| 6 | Audit uploads, downloads, changes, deletions, permission changes and refused attempts | Appends events for sign-in/failure, upload, preview open/page view, image preview, download, rename, delete, grant/update/revoke, admin role changes and denied attempts. Events have keyed HMAC-SHA-256 hashes using a separate stable application secret; ordinary UPDATE/DELETE is blocked by DB triggers; `/api/admin/audit/verify` verifies the chain. | Automated hash-chain and trigger tests. Residual: an operator who obtains the application HMAC key or can reset the app and database together can defeat database-local evidence; production needs a separately protected, external immutable checkpoint/log sink. |
| 7 | Search by name, owner, category and date | Authenticated document list supports `q`, `owner`, `category`, `from_date`, and `to_date` filters in SQL, before the result limit. | `test_challenge_requirements.py` checks filename/owner/category/date validation. Results never include documents not owned/shared with caller. |
| 8 | Validate uploaded files | Extension allowlist, byte-size limit, format signature checks, text binary rejection, Office ZIP path/entry/expanded-size checks; random storage keys and private storage. | `backend/tests/test_security_helpers.py` and API flow upload tests. This is not anti-malware scanning or a full parser sandbox. |
| 9 | Administrator view of document activity and permission changes | Admin-only overview, users/roles list and role management, active grants, global activity filters and audit-chain verification. Every `/api/admin/*` handler checks role on the server. | Admin dashboard frontend and admin API tests. Admin role is not a blanket content permission. |
| 10 | Automated tests show one user cannot reach another user's documents | Tests attempt unauthorised document list, preview, preview page/content, download, rename, shares and delete; then test grant/revoke and Reader/Editor boundaries. Audit integrity/update protection has direct tests. | Run `cd backend; python -m pytest -q`. Also perform final Compose/browser smoke tests; local test success does not substitute for the judge's deployed attack. |

## Final acceptance checks still required on the target machine

1. Rebuild `api` and `frontend` from the exact final source and inspect `docker compose ps` / logs.
2. Seed development demonstration accounts; change all sample credentials before public deployment.
3. Test PDF, DOC/DOCX, XLS/XLSX, PPT/PPTX, PNG/JPG, TXT and CSV preview in the rebuilt container. Office conversion requires LibreOffice and Poppler from the updated backend image.
4. Capture real HTTP responses for direct Reader download (403), access after revoke, and admin denial when no document grant exists.
5. Publish the repository and deploy to an HTTPS URL with seed data and role credentials. The ZIP alone is not a public repository or live deployment.
6. Record and provide the five-minute demo video; the included `DEMO_SCRIPT.md` is a script, not a video.
